# Iceberg Custom Elements 3.0.0 — automatic update design

## Intent and boundaries

Iceberg Custom Elements 2.3.1 is a modified copy of `soflyy/breakdance-custom-elements`. Make version 3.0.0 discoverable and installable through the existing `plugin.icebergwebdesign.com` update service, using the same WordPress update workflow as Iceberg Performance. WordPress should show an available update; each site owner may separately turn on WordPress's per-plugin Auto-updates. The plugin must not force background installation.

This stage delivers a plugin branch/PR, a reproducible release ZIP, tests, and a scoped registration of this slug and ZIP on the existing production update server, explicitly authorized by the owner after the initial spec review. Server deployment follows a tested artifact and a targeted backup; it does **not** merge to `main`, publish a GitHub release, or update an installed WordPress site.

The owner confirmed that installed sites use `wp-content/plugins/iceberg-custom-elements/plugin.php`, and Element Studio edits are centrally managed in the repository/release ZIP; site-local changes may be overwritten by a plugin update.

## Architecture and compatibility invariants

- Keep the plugin directory `iceberg-custom-elements/` and entry point `plugin.php`. Set WordPress plugin header version to `3.0.0`, and use one matching runtime version value. Set minimum metadata to WordPress `6.0` and PHP `8.0`, as the owner chose to match Iceberg Performance; set server `tested` metadata to WordPress `7.1.3`, the version the owner reports testing. A future GitHub release tag, if created, is `v3.0.0`; the WordPress/server version is `3.0.0`.
- Preserve the current `IcebergCustomElements` namespace, element IDs/classes, `elements/`, `macros/`, `presets/`, `registerSaveLocation()` calls, and `breakdance_loaded` priority 9. Avoid edits to element definitions/templates and unrelated menu enhancements. Breakdance need not be active for WordPress to check plugin updates.
- Put an updater class in a dedicated `includes/` file and bootstrap it independently from the Element Studio registration. Model its update hooks and request contract on Iceberg Performance: `pre_set_site_transient_update_plugins`, `plugins_api`, and `upgrader_process_complete`. Also hook `upgrader_pre_download` to refresh a signed package URL immediately before download. Scope every hook by plugin identity. Use `plugin_basename(__FILE__)` from the plugin entry point so the response key is exactly `iceberg-custom-elements/plugin.php`; the request slug is `iceberg-custom-elements`.
- Use the existing HTTPS server, `https://plugin.icebergwebdesign.com`, with its `version_check`, `plugin_info`, and `download` actions. Send the plugin slug/current version and the same environment fields as the working client. No GitHub token, license secret, or server private configuration is embedded in the plugin. The public server entry point requires the slug to be registered in its separate private `PluginRepository` configuration; that configuration is not in the `plugin` GitHub repo.
- Validate response shape and version before offering a package. Read-only inspection confirmed `version_check_response()` includes a signed `package` URL with a 900-second expiry. Use that URL to advertise the update, then bypass stale update transients by requesting a **fresh** signed URL at `upgrader_pre_download` and downloading it for this plugin only; on failure abort cleanly instead of attempting an expired URL. Reject missing/invalid or non-server package URLs, and do not construct the legacy unsigned download URL. Prevent interference with other plugins/WordPress.org by keeping filters scoped to this plugin and considering the WordPress `Update URI` header, verifying that it coexists with the existing transient-based updater.
- Cache valid update data for at most the working client's 12-hour interval; invalidate cache after this plugin upgrades. Invalid JSON, network errors, unknown slugs, missing packages, and maintenance responses must leave the plugin running and not create a broken update offer.

## Release artifact and server handoff

- Produce a ZIP with exactly one top-level directory `iceberg-custom-elements/`. Include `plugin.php`, `elements/`, runtime `includes/`, required `assets/`, and license/readme as applicable; exclude `.git`, test/build-only files, and the design/implementation documents. Verify ZIP contents and the plugin header version before handoff.
- After tests pass, back up the specific private server config and any target ZIP path outside the web root, record hashes/permissions, then add only the `iceberg-custom-elements` registration with version `3.0.0`, metadata, and `requires_license: false` like the two existing internal plugins. Place the tested ZIP at `/home/iceberg/private/plugins/iceberg-custom-elements/iceberg-custom-elements.zip` (the path derived by the existing `PluginRepository::zip_path()`). Preserve the registered `iceberg-addons` and `iceberg-performance` entries byte-for-byte. Read back the deployed files and probe the three server actions without displaying signed URLs or secrets. If registration/ZIP validation fails, restore only the touched files. The server remains the source of installable packages rather than GitHub's autogenerated source ZIP.
- Installation on a staging site, when one is available and separately authorized, should confirm that `2.3.1` detects `3.0.0`, package download installs over the existing folder instead of creating a duplicate, both shipped elements still render, and Element Studio can edit/save to the same locations. No live WordPress plugin updates are in scope.

## Verification

- Automated updater tests with mocked WordPress hooks/HTTP: correct plugin basename/slug, newer/equal/older versions, failure/invalid/missing data, cache reuse/invalidation, plugin-info scoping, no forced auto-update setting, plus expired signed URL refreshed immediately before download for the target plugin only (including bulk/automatic update paths), and clean failure rather than stale fallback.
- Check Breakdance integration via source-level invariants and, when an appropriate test environment is available, an actual Breakdance/WordPress staging smoke test. Tests should not claim live compatibility without that runtime check.
- PHP syntax checks plus available repo test tooling; if PHP/WordPress/Breakdance cannot be run, report that limitation explicitly rather than claiming tests passed.
- ZIP inspection asserts paths and version. Compare the proposed PR against `main` to ensure no unintended element/template changes. Review the diff before committing/pushing. CI status must be reported only after a fresh read.

## Risks and assumptions

- Server `private/config.php` and `private/lib/PluginRepository.php` are not in the examined GitHub repo. Read-only SSH inspection confirmed the current private config registers `iceberg-addons` and `iceberg-performance` but not `iceberg-custom-elements`; it also confirmed signed package URLs expire after 900 seconds. Server registration can be verified independently, but do not report site-level automatic updates as operational until an actual staging upgrade passes.
- Updating the plugin will replace files under `elements/`, `macros/`, and `presets/`; accepted because the owner centrally manages them in releases. Take a staging backup of any site-local edits before the first rollout.
- Registration on the production update server is a narrow, explicitly approved write. Existing server backups are not a substitute for a fresh targeted backup and readback of the exact touched files. No production WordPress site changes or main-branch merge are in scope.
